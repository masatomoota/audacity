### [H1] CallbackDoSeek acquires mutex on the RT callback thread, blocking StopStream deadlock

- **場所**: `libraries/lib-audio-io/AudioIO.cpp:3232-3289`
- **種別**: deadlock  / 領域: audioio-core  / finder確信度: high  / 申告重大度: critical → 修正後: high
- **内容**: CallbackDoSeek() is called directly from the PortAudio RT callback thread (via FillOutputBuffers -> CallbackDoSeek at line 2699). It immediately tries to acquire mSuspendAudioThread (a wxMutex) at line 3235. Meanwhile, StopStream() on the main/UI thread first sleeps for up to `latency+50` ms (line 1468) then acquires the same mSuspendAudioThread at line 1472. If the user triggers Stop while a seek is happening, the PortAudio callback holds or is waiting for mSuspendAudioThread while StopStream waits to acquire it — a standard mutex-on-RT-thread scenario that stalls the audio hardware callback. Worse, CallbackDoSeek also calls ProcessOnceAndWait() at line 3283 while holding mSuspendAudioThread: ProcessOnceAndWait signals the audio worker thread and then busy-waits (50ms sleeps) for it to finish. The audio worker thread's loop body at lines 1782-1831 calls SequenceBufferExchange() which may itself try to take locks in disk/effect code. This is a priority-inversion and potential deadlock: the high-priority PA callback thread is sleeping inside the lock, starving the main thread which is also trying to grab that same lock.
- **再現/到達性**: Any user-triggered keyboard seek (SelectMenus.cpp line 167 calls SeekStream() setting mSeek) while the stream is active will cause FillOutputBuffers to enter CallbackDoSeek on the next callback invocation. StopStream() acquires mSuspendAudioThread on the main thread at line 1472. These two paths race for the same mutex, with the RT callback thread holding it while performing milliseconds-scale waits. This scenario is straightforwardly reachable: seek key held, user presses stop.
- **検証(verifier)**: The mechanism is real and reachable. CallbackDoSeek() at line 3232 is called directly from the PA RT callback via FillOutputBuffers (line 2699). It immediately acquires wxMutex mSuspendAudioThread at line 3235 (confirmed: only two lock sites exist for this mutex — lines 1472 and 3235). While holding that mutex, it: (1) busy-sleeps in 50ms increments at lines 3254-3259 waiting for the audio worker thread to stop, then (2) calls ProcessOnceAndWait() at line 3283 which busy-sleeps again waiting for the audio worker to run once. StopStream() on the main thread acquires the same mSuspendAudioThread at line 1472 after an optional latency sleep. If a seek is in progress (mSeek != 0) when StopStream() runs, the RT callback holds the mutex for up to hundreds of milliseconds of sleep while StopStream blocks. This is not a theoretical deadlock scenario: the audio worker thread can still run (mSuspendAudioThread does not block it), so the sleeps will eventually terminate and the mutex will be released. However, the priority inversion is genuine: a high-priority RT audio callback thread holds a mutex while sleeping, causing the main UI thread to be blocked for the full duration of those sleeps (potentially 50-200ms). If the audio worker thread itself is slow (disk I/O, effect processing per lines 1782-1831), StopStream can stall visibly. The corrected severity is high rather than critical because it is not an infinite deadlock — the audio worker thread is not waiting for mSuspendAudioThread, so it can eventually clear the atomic flags and end CallbackDoSeek's sleep loops — but the stall is deterministically reachable by holding a seek key and pressing stop.

### [H2] MP3 ID3 end-of-file write error check uses wrong variable

- **種別**: logic  / 領域: export-codecs  / finder確信度: high  / 申告重大度: high → 修正後: high

```cpp
if (bytes > (int)context.outFile.Write(context.id3buffer.get(), context.id3len)) {
    throw ExportErrorException("MP3:1997");
}
```

The correct pattern used on lines 1995 and 2015 is `if (N > outFile.Write(..., N))`. Here, N should be `context.id3len`, not `bytes`. ### [H4] wxUint32 chunk-length overflow causes infinite loop in WAV/AIFF ID3 scanner

- **場所**: `modules/import-export/mod-pcm/ImportPCM.cpp:453-463`
- **種別**: integer-overflow  / 領域: import-pcm-raw  / finder確信度: high  / 申告重大度: high → 修正後: high
- **内容**: The RIFF/AIFF chunk scanner reads a 32-bit chunk length into `wxUint32 len` and advances with `f.Seek(len + (len & 0x01), wxFromCurrent)` to skip non-ID3 chunks. If an attacker (or corrupt file) sets `len = 0xFFFFFFFF` (the maximum odd 32-bit value), the expression `len + (len & 0x01)` evaluates entirely in wxUint32 arithmetic: `0xFFFFFFFF + 1 = 0x00000000` (wraps to zero). `f.Seek(0, wxFromCurrent)` is a no-op; the file position does not advance. The next iteration reads the same 4-byte chunk ID and length again, repeating forever. The loop guard is `while (!f.Error())`, which never triggers because the seek and read both succeed.
- **再現/到達性**: Any WAV or AIFF file (which Audacity opens via PCM import) with a crafted 4-byte chunk-length field of 0xFFFFFFFF triggers this path. The file need only have a non-ID3 chunk header near the tail; the scan loop then hangs permanently, blocking the UI thread.
- **検証(verifier)**: At line 463 of ImportPCM.cpp, `len` is declared as `wxUint32`. The expression `len + (len & 0x01)` is evaluated entirely in `wxUint32` arithmetic. When `len = 0xFFFFFFFF` (max odd 32-bit value), `(len & 0x01)` is 1, so the sum is `0x100000000` which wraps to `0x00000000` in `wxUint32`. The value `0` is then implicitly widened to `wxFileOffset` (64-bit) before being passed to `wxFFile::Seek(0, wxFromCurrent)` — a no-op. The file position does not advance. The loop condition `while (!f.Error())` never triggers because both the seek of 0 and the re-read of the same 4-byte chunk header succeed. There are no iteration counters, no EOF-position tracking, no timeout guards, and no size validation on `len` before use in the seek. Any WAV or AIFF file with a non-ID3 chunk whose 4-byte length field is 0xFFFFFFFF will cause a permanent hang in the UI thread during tag import. The bug is real and reachable via a crafted or corrupt file.

### [H5] COMMIT return value silently ignored in CopyTo — corrupt destination delivered as success

- **再現/到達性**: Disk-full conditions are realistic during Save As or Compact operations on large projects. SQLite documents that COMMIT can fail and that callers must check the return code. The cleanup lambda (lines 978–1014) only runs when `!success`, which does not get set in this path because the check is entirely absent. This bug would cause total audio data loss disguised as a successful save.
- **検証(verifier)**: The COMMIT return value is genuinely unchecked at line 1164. The failure path is: (1) COMMIT fails (e.g., SQLITE_FULL on disk-full), causing SQLite to automatically roll back the transaction on the 'outbound' attached database; (2) with no active transaction remaining, DETACH at line 1168 succeeds on the now-empty outbound DB — SQLite only refuses DETACH when there are active statements or transactions, and a failed COMMIT ends the transaction; (3) DETACH succeeds, so `success = true` is set at line 1182; (4) the cleanup lambda at lines 978-1014 only runs when `!success`, so it does NOT delete the destination file; (5) the destination file is a valid SQLite database with schema tables but zero rows.

The project then appears to switch to the new empty file, causing data to be inaccessible, though the original file still exists on disk.

The claim's description is accurate about the mechanism. The corrected severity is high (not critical) because: the trigger requires a disk-full condition timed precisely during COMMIT (not writes), which is realistic but not the common case; and for Save As, the original project file is not immediately destroyed. For Compact, the scenario is closer to critical since the original is actually deleted.

### [H6] Visit() iterates mStates without the spinlock, racing with Add/Remove/Move on main thread

- **場所**: `libraries/lib-realtime-effects/RealtimeEffectList.h:84-96`
- **種別**: data-race  / 領域: realtime-effects  / finder確信度: high  / 申告重大度: critical → 修正後: high
- **内容**: RealtimeEffectList::Visit() (called from all three RT-thread entry points: ProcessStart, Process, ProcessEnd) reads mStates — a std::vector<shared_ptr> — without holding mLock. Concurrently, AddState/RemoveState/ReplaceState/MoveEffect on the main thread swap a newly-built copy into mStates under a very brief lock_guard. The lock duration is intentionally tiny: `(LockGuard{ mLock }, swap(shallowCopy, mStates))`. Between the lock release and the RT thread's next iteration, the RT thread may be mid-range-for over the old vector, but the swap may have already completed. A std::vector copy-and-swap is safe only if the reader also takes the lock. Because Visit never acquires mLock, the RT thread can observe a partially destroyed vector (the old one is being destroyed on the main thread while the RT thread still holds an iterator into it).
- **再現/到達性**: The pattern works for pointer-sized atomics but std::vector is not atomically swappable on any real architecture. The RT thread enters Visit and gets a raw begin/end from mStates. Meanwhile the main thread calls RemoveState: copies mStates into shallowCopy, erases from shallowCopy, then acquires the lock and swaps shallowCopy↔mStates. After the swap, the old mStates (now in shallowCopy) is destroyed, decrementing refcounts of shared_ptrs. If the RT thread is mid-iteration over the now-destroyed vector it reads freed memory. This is a textbook TOCTOU/data-race on a std::vector.
- **検証(verifier)**: The code at RealtimeEffectList.cpp lines 97-100, 124-135, 154-163, 176-180, 222-239 all follow the same pattern: build a shallowCopy on the main thread, then do `(LockGuard{ mLock }, swap(shallowCopy, mStates))` — the lock guard is destroyed at the end of that comma-expression, and then shallowCopy (holding the old vector) is destroyed on the main thread. Visit() at lines 84-96 of the header iterates `mStates` directly with no lock acquired anywhere in the call chain (VisitGroup/VisitAll in RealtimeEffectManager.h lines 168-193 call `.Visit(func)` without any lock). The spinlock `mLock` is acquired only for the duration of `std::vector::swap`, which modifies the vector's internal buffer pointer, size, and capacity fields. The RT thread doing a range-for over `mStates` reads those same fields (begin/end via the internal pointer+size) without holding `mLock`. This is a textbook C++ data race: concurrent unsynchronized read (RT thread) and write (main thread's swap) on the same std::vector object. The old vector's destruction on the main thread after the lock is released while the RT thread may still be iterating into the (now-swapped-out) buffer is an additional use-after-free path. The bug is real and reachable whenever a user adds/removes an effect while audio is playing. Severity is high rather than critical because (a) the window is narrow — the swap is fast — and (b) the shared_ptr elements keep the underlying RealtimeEffectState objects alive even after the vector buffer is released, so the most likely symptom is a corrupted iteration (wrong element count or a crash from reading the vector's metadata) rather than immediate freed-memory access into state objects themselves.

### [M3] Non-atomic mSeek written by main thread, read/written by RT callback — data race

- **内容**: mSeek is declared as plain `double mSeek` (AudioIO.h line 285, not std::atomic). SeekStream(double seconds) at AudioIO.h line 482 does a bare `mSeek = seconds` from the UI/main thread. - **再現/到達性**: SeekWhenAudioActive (SelectMenus.cpp line 167) calls gAudioIO->SeekStream() from a keyboard/menu handler on the main thread while the PA stream is running. The PA callback fires concurrently on a different thread reading that same double. No synchronization separates them.

  理由: The `+0.5` bias in `GetTotalNumSamplesToProduce` (line 37) is a deliberate rounding guard. ## A1. RealtimeEffectManager `mSuspended` → ❌ revert 維持（再適用しない）
- 調査で revert 理由が判明: 同一修正(c2f4e8acd)は **pause/unpause で RealtimeSuspend/Resume を正しく発火させ、その結果 CompressorInstance の RealtimeResume → DynamicRangeProcessorHistoryPanel が履歴グラフに不要なセグメント区切りを入れる回帰**を生んだ。upstream は修正を revert し、症状側を別途処理(7787bc1b3)。
- 元の"バグ"（pause 中に suspend ヒントが伝播しない）は**ほぼ無害**（再生中は false=現状と同じ、pause 時のみ差。suspend/resume は基本ヒント）。再適用は履歴グラフ回帰を再導入する。
- **結論**: 再適用しない。直すなら Compressor 履歴パネルの resume サブスクリプション側の整理が前提＝別 wave・要 UX 判断。

## A2. RealtimeEffectState `Finalize` の mWorkerSettings 競合 → ✅ 安全修正を実装
- 調査で確定: 競合は **RemoveState/ReplaceState の hot-removal 経路**で実在（main の Finalize が、RT スレッドが旧スナップショットで処理中=mWorkerSettings 書込中に読む）。通常停止経路(Manager::Finalize)は RT join 済で安全。
- **修正**: `Finalize(bool rtStopped)` 化。`mMainSettings = mWorkerSettings` のコピーは **rtStopped=true（通常停止）時のみ**実行。hot-removal(false) では skip（mMainSettings は直前の `Access::Flush()` で同期済のため設定喪失なし）。
  - 変更: `RealtimeEffectState.{h,cpp}`（シグネチャ＋ガード）、`RealtimeEffectManager.cpp` 3呼出（Manager::Finalize=true、ReplaceState/RemoveState=false）。
  - 「コピー削除」案(前 wave で revert したもの)と違い、**通常経路の最終設定保存を維持**しつつ競合のみ解消。

## H1. AudioIO `CallbackDoSeek` デッドロック/スタール → ⏸ 見送り（設計結論）
- 全制御フロー分析: `mSuspendAudioThread` は **StopStream と CallbackDoSeek の相互排他**（再生状態のティアダウン vs seek 中のバッファ再配置の競合防止）を担う必須機構。無限デッドロックではなく、seek 直後 stop 時の**有界スタール（〜数百ms）**。
- 候補評価: (a) StopStream の try-lock 化 → ループ内でイベントポンプしない以上ハードブロックと実質同等で**改善にならない**（ポンプは再入で危険）。(b) CallbackDoSeek の critical section 縮小 → **use-after-free を生む危険**。(c) seek を worker へ委譲 → 正攻法だが大規模・新規競合リスク・要実機テスト。(d) 現状維持。
- **結論**: 安全かつ実効ある局所修正は存在しない。現状維持を推奨。恒久対応は (c) を専用タスク＋再生/seek/stop 実機テストで。関連 `mSeek` データ競合は atomic 化済み。
